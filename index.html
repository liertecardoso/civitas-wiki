A arquitetura em quatro frases

  1. São dois repositórios: civitas-auth (Authentication, User, RBAC) e civitas-api (Tenant e Core).
  2. Cada serviço é publicado como um Container App próprio no Azure.
  3. São dois bancos PostgreSQL: cp_identity (identidade e acesso) e civitas_db (tenants e dados de domínio).
  4. Cada tenant tem o seu próprio schema dentro do civitas_db. Os dados de um cliente nunca ficam em tabelas compartilhadas com outro.

Visão Geral

O Civitas é a plataforma de segurança da Brasiline / ARX Cyber. Ela concentra, para cada cliente, as informações das ferramentas de segurança que ele usa e entrega visão de ativos, exposições, riscos e relatórios, operada pela ARX através do SecOps.

Premissas do produto

  • O cliente nunca cria uma conta nova: entra com Microsoft Entra ID ou Google Workspace.
  • O volume de dados por cliente é muito grande, vindo de várias ferramentas de segurança.
  • Os clientes são majoritariamente Microsoft; a plataforma roda no Azure, região Brazil South.

Por que o login não depende do civitas-api

O Authentication mantém uma cópia do status de cada tenant (ativo, suspenso, desativado), atualizada pelos eventos do tópico civitas-tenant. Se o civitas-api cair, os logins continuam funcionando. O login local da ARX (break-glass) nunca consulta o Tenant Service.

Arquitetura

Isolamento de Dados

Regra principal: cada tenant tem o seu próprio schema PostgreSQL dentro do banco civitas_db. Os dados de domínio de um cliente (monitoramento, auditoria do cliente e, no futuro, ativos e findings) só existem dentro do schema dele. Nenhuma tabela de domínio fica no schema public ou compartilhada entre clientes.

Por que um schema por tenant

O volume de dados por cliente é muito grande, vindo de várias ferramentas de segurança. Com um schema por tenant:

  • As tabelas de um cliente não crescem com os dados dos outros, e os índices ficam menores.
  • Exportar ou restaurar um cliente é um pg_dump -n tenant_<id>.
  • Excluir um cliente (cancelamento, LGPD) é um DROP SCHEMA, não um DELETE em milhões de linhas.
  • Um erro de filtro no código não expõe dados de outro cliente, porque as tabelas são fisicamente separadas.

A decisão está registrada em ADR-002.

Resumo: identidade, acesso e catálogo são compartilhados e protegidos por tenant_id; dados de domínio são isolados por schema.

O administrador do cliente não tem tabela própria. Ele é um usuário normal em identity.users, com o papel Tenant Admin em rbac.tenant_memberships (ADR-014).

Situação em 2026-10-13: hoje o civitas_db tem os schemas compartilhados audit e monitoring. Na entrega da parte de tenants (até 2026-10-15), audit_events e monitoring_* passam para dentro de cada tenant_<id>. O schema audit permanece só para a auditoria global, de ações que não pertencem a nenhum cliente.

Como funciona na prática

  1. Criação. No provisionamento, o Tenant Service cria o schema tenant_<id>, aplica nele todas as migrações de domínio e registra o nome do schema no catálogo (tenancy.tenants).
  2. Nome do schema. Sempre tenant_<id>, onde <id> é o identificador imutável do tenant. Nunca é derivado do nome ou slug do cliente, que podem mudar.
  3. Cada requisição. O pacote comum lê o tenant do token, busca o schema no catálogo (com cache) e executa SET LOCAL search_path TO tenant_<id> dentro da transação.
  4. Nunca a partir da requisição. O schema vem só do token validado. Nenhum parâmetro de URL, corpo ou cabeçalho escolhe o schema.
  5. Sem SQL com nome de schema montado à mão. O código usa o contexto do pacote comum; concatenar nome de schema em SQL é proibido.
  6. Migrações. Toda migração de domínio roda em todos os schemas de tenant listados no catálogo (ver Migrações de Banco).
  7. Exclusão. Ao fim do período de retenção, DROP SCHEMA tenant_<id> CASCADE (ver Tenants).

Atenção com pool de conexões. Use sempre SET LOCAL dentro de uma transação. Um SET search_path sem LOCAL fica preso na conexão e pode vazar para a próxima requisição de outro cliente que reutilizar a mesma conexão do pool.

Testes obrigatórios de isolamento

  • Requisição com token do tenant A não lê nenhum dado do schema do tenant B, mesmo alterando IDs na URL.
  • Duas requisições seguidas de tenants diferentes na mesma conexão do pool usam cada uma o seu schema.
  • Requisição sem tenant no token não acessa nenhum schema de tenant.

Limites e evolução

O modelo de schema por tenant atende bem centenas de clientes no mesmo banco. Dois caminhos ficam previstos para quando o volume exigir, sem mudar o código dos serviços:

Situação Evolução Campo no catálogo
Cliente muito grande ou com exigência contratual Mover o schema dele para um banco ou servidor dedicado isolation_level = dedicated_db
Eventos brutos em volume muito alto Armazenar em Azure Data Explorer, um database por tenant A definir com a camada de integração

Arquitetura

Eventos

O Service Bus carrega avisos de que algo mudou no plano de controle. Dados pesados dos clientes não passam por ele.

Como um evento nasce

  1. O serviço altera o próprio banco e grava o evento na tabela audit_outbox do seu schema, na mesma transação.
  2. O Outbox relay lê os audit_outbox de todos os serviços e publica no Service Bus.
  3. Depois de publicado, o registro é marcado como enviado.

Assim, um evento só existe se a alteração realmente aconteceu, e nenhum evento se perde se o Service Bus ou o Core estiverem fora do ar.

Regras para os consumidores

  • Entrega pelo menos uma vez: o mesmo evento pode chegar duas vezes. Todo consumidor verifica o event_id antes de processar.
  • Dead-letter queue: mensagem que falha várias vezes vai para a DLQ e gera alerta. Nunca é descartada em silêncio.
  • Ordem por tenant: o tenant_id é usado como sessão do Service Bus, para que, por exemplo, tenant.suspended nunca seja processado antes de tenant.created.

O que não passa pelo Service Bus

  • Dados de monitoramento e de integrações (alto volume): Event Hubs, quando os conectores chegarem.
  • Consultas que precisam de resposta imediata: chamada HTTP à API do outro serviço.
  • Mudança de papel no token: entra na próxima renovação do token.

ADR-018 — Esteira contínua de tratamento com arquivo bruto e reprocessamento

Campo Valor
Status Proposta
Data 2026-10-14
Responsável Jonas Alfonso
Aprovado por A preencher

Contexto

O volume das integrações é muito grande e chega o tempo todo. Tratamento em lote manual não acompanha, e um erro de mapeamento pode corromper dados sem possibilidade de recuperação.

Decisão

Event Hubs recebe tudo, com partição por tenant. O Capture grava o bruto continuamente em Blob ou ADLS. Gravar direto do coletor no banco Sem buffer, sem reprocessamento, um cliente com pico derruba os outros
Processamento em lote agendado Atraso alto para alertas

ADR-019 — OCSF como base do modelo normalizado

Campo Valor
Status Proposta
Data 2026-10-14
Responsável Jonas Alfonso
Aprovado por A preencher

Contexto

Cada fabricante descreve o mesmo fato com campos diferentes. Sem um modelo comum, cada módulo do Civitas precisaria entender cada fabricante.

Decisão

Os conectores convertem os dados para classes do OCSF (Open Cybersecurity Schema Framework): Network Activity para logs de firewall, Findings para achados, Discovery para inventário. Campos sem equivalente vão para uma extensão do Civitas.

Consequências

Módulos e relatórios funcionam igual para Fortinet, Microsoft e os próximos fabricantes. Padrão aberto, já adotado por vários fornecedores de segurança. Em troca, mapear para OCSF dá mais trabalho no conector do que um modelo próprio simples.

Alternativas consideradas

Alternativa Por que não
Modelo próprio do Civitas Reinventa o que já existe e dificulta integrações futuras
Guardar só no formato de cada fabricante Cada módulo precisaria conhecer cada fabricante

Provisionamento

Cada passo é idempotente.

  1. Registrar o tenant em tenancy.tenants com status provisioning.
  2. Criar o schema tenant_<id> no civitas_db.
  3. Aplicar no schema todas as migrações de domínio.
  4. Registrar no catálogo o nome do schema.
  5. Registrar módulos (tenant_modules) e contrato (tenant_contracts).
  6. Criar o administrador local do cliente como usuário normal (User) com credencial break-glass e MFA obrigatório no primeiro acesso (Authentication) — RN-04, ADR-014.
  7. Vincular esse usuário ao tenant com o papel Tenant Admin (RBAC).
  8. Mudar o status para active e gravar tenant.created no audit_outbox; o Authentication atualiza o cache ao receber o evento.

Descomissionamento

  1. Suspender: logins bloqueados, dados mantidos.
  2. Iniciar decommissioning: começa o período de retenção (30 dias, RN-19; exportação ao cliente em P-05).
  3. Ao fim do período: exportar o schema se o contrato pedir, executar DROP SCHEMA tenant_<id> CASCADE e apagar os arquivos do tenant.
  4. Manter só o registro mínimo do tenant e a trilha de auditoria.

A rotina automática de exclusão (passo 3) não faz parte da sprint atual.

Integrações

A camada de integração coleta dados das ferramentas de segurança dos clientes e os converte para o modelo do Civitas. Cada fabricante tem conectores versionados (RN-12): várias versões do mesmo conector convivem, porque os clientes mantêm versões antigas dos produtos.

Fabricante Páginas Situação
Fortinet (FortiAnalyzer, FortiGate) Visão geral · Coleta · Dados e armazenamento · Backoffice Proposta para validação
Microsoft (Defender, Entra, Sentinel) A documentar Planejado
Todas Tratamento contínuo dos dados Proposta para validação

Princípios para todas as integrações

  • O cliente nunca expõe a gerência dos equipamentos à internet para o Civitas. A coleta acontece por um coletor instalado na rede do cliente, com conexão só de saída (ADR-015).
  • Somente leitura. As credenciais que o cliente cria para o Civitas têm perfil de leitura. O Civitas não envia comandos aos equipamentos.
  • Credenciais no Key Vault, separadas por tenant, nunca no banco nem em log.
  • Dado bruto e dado normalizado separados. O bruto fica guardado como chegou; o normalizado segue o modelo do Civitas (ativos, findings, alertas).
  • Cada conector declara as versões que suporta. O coletor detecta a versão do equipamento e escolhe o conector certo.

Fortinet: coleta

Conectividade: coletor na rede do cliente

O FortiAnalyzer e os FortiGates ficam na rede do cliente. Para o Civitas chamar as APIs direto do Azure, o cliente teria de expor a interface de gerência à internet, e isso é justamente o que as vulnerabilidades recentes exploram. A CVE-2024-55591 (bypass de autenticação no FortiOS, CVSS 9,8) foi explorada em interfaces de gerência expostas e entrou no catálogo KEV da CISA no dia da divulgação, em 14/01/2025 (CVE-2024-55591 (Censys)).

Por isso, a proposta é um Coletor Civitas instalado no cliente (ADR-015):

FortiAnalyzer: encaminhamento de logs

O FortiAnalyzer encaminha logs para servidores syslog ou CEF (Log forwarding do FortiAnalyzer; referência oficial: FortiAnalyzer 7.4 Administration Guide: Configuring log forwarding):

  • Conexão confiável (TCP) ou UDP; com TCP, se a conexão cair, os logs ficam em buffer de até 12 GB e são reenviados.
  • Filtros por dispositivo e por condições de campo do log.
  • Exclusão de campos por tipo de dispositivo e tipo de log (syslog e CEF).

O destino é o coletor do cliente, que recebe localmente e envia ao Civitas. Na fase 3, encaminhar só os tipos combinados (eventos, IPS, antivírus), nunca o tráfego completo.

Fortinet: dados e armazenamento

Cada tipo de dado vai para o armazenamento que combina com o volume e o uso dele, sempre isolado por tenant. Logs de tráfego não são copiados para o Civitas: ficam no FortiAnalyzer do cliente e são consultados sob demanda (ADR-016).

Por que não copiar o tráfego

A própria Fortinet estima o volume a partir de cerca de 1 log de tráfego por sessão, com 700 a 800 bytes por log (Estimativa de banda de log FortiGate → FortiAnalyzer). Um FortiGate com 1.000 novas sessões por segundo gera:

Cenário Banda Volume aproximado por dia
Só tráfego, sem compressão 6,4 Mbps ~69 GB
Só tráfego, TCP confiável (compressão ~3:1) 2,13 Mbps ~23 GB
4 tipos de log por sessão, TCP confiável 8,53 Mbps ~92 GB

Os volumes por dia são conversão nossa a partir da banda do artigo. Multiplicado por vários FortiGates e vários clientes, copiar tudo transforma o Civitas em um SIEM, com o custo de um SIEM. O cliente já guarda esses logs no FortiAnalyzer.

Cadastro de uma integração FortiAnalyzer

  1. Escolher o tipo FortiAnalyzer e o coletor do cliente.
  2. Informar o endereço interno e o ADOM.
  3. Colar a chave de API. Ela vai direto para o Key Vault; o Civitas nunca mais a exibe.
  4. Testar conexão: o coletor chama /sys/status e mostra a versão detectada, o conector que será usado e as permissões da chave. Se a chave tiver permissão de escrita, o Civitas avisa e recomenda trocar por uma somente leitura.
  5. Escolher o que coletar: inventário (padrão), alertas (padrão), agregados, encaminhamento de logs.
  6. Definir a frequência: inventário a cada 6 horas e alertas a cada 5 minutos (valores a validar).
  7. Salvar. A primeira coleta roda na hora e o resultado aparece na tela.

O assistente mostra o passo a passo para o cliente criar a credencial no próprio equipamento:

No ADX, o cache quente e a retenção são políticas independentes. Com retenção de 56 dias e cache de 28, os 28 dias mais recentes ficam em SSD e o restante em armazenamento mais barato, e as consultas continuam vendo os 56 dias (Caching policy do Azure Data Explorer).

Escala

  • Workers escalam pela fila: no Container Apps, o número de instâncias acompanha a quantidade de eventos pendentes no Event Hubs, pelo scaler azure-event-hub do KEDA (Escala por KEDA no Container Apps (scaler azure-event-hub)). Sem fila, voltam ao mínimo.
  • Partição por tenant: a ordem é garantida dentro de cada cliente, e um cliente com pico não bloqueia os demais.
  • Cliente grande: pode ganhar Event Hub e workers dedicados, no nível de isolamento dedicated_workload já previsto no catálogo de tenants.

Cota e custo por tenant

O custo cresce com o volume de cada cliente, então o volume precisa ser contratado e acompanhado:

Situação Ação automática
Tenant acima de 80% do volume diário contratado Alerta para a ARX no SecOps
Tenant acima de 100% Alerta para a ARX e para o admin do cliente; dados continuam entrando
Aumento súbito (por exemplo, 3 vezes a média) Alerta de possível erro de configuração no cliente

Eventos de segurança (alertas, IPS, antivírus) nunca são descartados por cota. Amostragem só se aplica a logs de baixo valor e é decisão de negócio (P-16).

Migrações de Banco

Existem dois tipos de migração, com regras diferentes.

Migrações de controle

Schemas auth, identity, rbac (cp_identity) e tenancy (civitas_db). Rodam uma vez, no repositório do serviço dono do schema. Nenhum serviço altera schema de outro.

Migrações de domínio (schemas de tenant)

Tabelas do Core e dos módulos de produto. Precisam chegar a todos os schemas tenant_<id>.

  1. A migração é escrita e versionada uma única vez no civitas-api.
  2. No deploy, o pipeline lista os schemas de tenant no catálogo (tenancy.tenants) e aplica a migração em cada um.
  3. A versão aplicada fica registrada dentro de cada schema (tabela de controle da ferramenta de migração).
  4. Falha em um schema não bloqueia os outros: o tenant fica marcado para nova tentativa e gera alerta.
  5. Um tenant novo recebe todas as migrações no provisionamento.

Regras para escrever migração de domínio

  • Compatível com a versão anterior do código (adicionar coluna antes de usar, remover só depois).
  • Sem nome de schema escrito na migração: ela roda com o search_path do tenant.
  • Testada em pelo menos dois schemas de tenant antes do merge.
